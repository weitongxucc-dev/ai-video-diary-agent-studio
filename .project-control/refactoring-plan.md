## 1. 给用户看的结论

代码需要系统性拆分。现有问题集中在：一个入口文件承担很多业务；后台执行借用HTTP路由；仓储同时处理过多对象和计算；业务依赖隐含上下文；多个入口分别解释状态。

保留本地单体、现有SQLite、任务与版本事实链、原素材和已存在的媒体执行基础。重构改变内部职责和调用方向，不以改数据库格式、改产品流程或更换框架作为起点。

第一批从“只修改第二个短镜头，得到修改前后预览，其他内容不变”贯穿真实路径。它是验证拆分方法的起点，整体范围还包括全部活跃创作与资产能力、调度、对话与CLI、Web、桌面壳和手机内部结构。不能修完一个案例就宣布全面重构结束。

用户可按四个结果验收：操作成功且目标正确；其他内容和原有能力保持；应用、撤销、保存及重启结果一致；后续修改主要落在对应模块，减少无关联动。内部规则和文件划分由技术负责人负责，不把这些选择交给代码初学者。

### 2.2 已确认的具体耦合

- main中的_execute_task_media_operation构造Starlette Request，依据路由函数签名恢复参数，再调用路由函数。后台业务因此依赖HTTP层。
- _task_media_route同时承担幂等、权限、版本、收集媒体参数、决定同步/排队及回执保存；很多动作通过TaskMediaRequired和ContextVar改变执行路径。
- main多处直接访问production_repo._connect和conversation_repo._connect；对应写入规则散在仓储之外。
- 导入main会读取Settings并创建仓储、模型、媒体等全局对象；[conftest.py](../apps/api/tests/conftest.py)必须提前隔离路径和配置来保护真实数据库。
- 调色短预览使用整片CPU渲染预算。该问题需要执行用途与实测资源契约修复，移动文件不能解除阻断。

### 2.3 必须保留的有效基础

- CreationTask、TimelineVersion、EditOperation、JobRun、ArtifactRecord和TaskEvent的既有关系与历史。
- [confirm_edit_proposal](../apps/api/app/production.py)的完整保存及版本检查机制；图像、音频、字幕和依赖需要一致提交。
- [linked_timeline.py](../apps/api/app/linked_timeline.py)的统一时间区间映射；拆计算代码不能让各轨分别推导时轴。

- 已采用共同schema的Pi/CLI入口、现有对象授权、本地文件引用和媒体校验。

## 4. 关键技术决定

### 4.1 一个业务动作，一个明确调用入口

以“准备局部画面预览”为例：

1. HTTP/Pi/CLI解析外部输入，得到可信操作者与请求身份。
2. 具体用例读取任务、期望版本、选中镜头及授权来源，计算修改前后候选与实际预览区间。
3. 媒体能力声明该候选的资源需求；用例提交既有持久作业，返回原请求定位。
4. 设备协调者决定准入，执行器直接消费封存输入，不调用路由，也不再反射路由函数签名。
5. 校验实际媒体后登记产物和回执；用户采用另走同一编辑保存入口，正式出片由明确生成动作启动。

元数据编辑直接保存；需要媒体计算的预览明确提交作业。把当前“先调用一次路由、抛出TaskMediaRequired后再排队重入”的隐含协议，逐项替换为明确的命令与作业提交，不改变用户确认语义。

### 4.2 契约按真实边界定义

| 契约 | 必须明确的事实 | 归属 |
| --- | --- | --- |
| 操作者与来源 | 可信成员/空间、原请求身份、轮次或外部来源 | 认证入口与现有后台身份复核 |
| 编辑命令 | 动作、目标、期望版本、参数patch、单位 | 创作编辑能力 |
| 预览输入 | 封存候选、实际区间、源修订、画幅、音轨/字幕/图层范围 | 媒体预览用例 |
| 执行要求 | 工作用途、真实输入量、计算规模、输出/临时文件上限和时限 | 具体执行能力；调度只消费 |
| 执行上下文 | 原作业与许可、截止时间、取消、进程及输出额度 | 既有设备执行层 |
| 产物与失败 | 实测信息、摘要、来源、版本、范围、失败类别和可执行下一步 | 实际执行/登记；适配层转换展示 |

复用现有类型和共同能力目录，保持外部schema、字段单位及请求定位兼容。只抽取真正被多方消费的契约；Pydantic或dataclass不是层次判断标准，类型模块应避免启动模型、仓储或进程。领域和执行用例不返回HTTPException、Request或JSONResponse；这些转换留在入口。

ContextVar可以保留追踪用途；操作者、期望版本和设备许可不再仅从环境上下文取得。显式上下文不是让调用方自报可信身份，仍须由已有边界构造与复核。

### 4.3 事务与产物提交

- 数据库继续使用现有表和对象身份；第一阶段不迁移字段格式。拆仓储实现时共用明确事务入口，不各自独立commit。
- 编辑计算形成变更集；一个事务同时比较基础版本、写操作与新版本、更新任务/音轨/字幕及依赖。并发冲突保持原语义。
- 文件系统与SQLite不是同一个原子事务。保留暂存、实测、发布、登记与恢复证据，故障注入分别覆盖文件已发布但登记未完成、登记后回执中断；不以“统一事务”掩盖这个边界。
- 不在持有长数据库写锁时运行FFmpeg、模型或等待网络；提交前重新核验封存身份与修订，晚产物保留历史，不覆盖新编辑。
- 任务状态、作业状态和许可状态各由现有负责人维护，同一结果经只读投影展示，不新增通用“完成”表或模型自评成功库。

### 4.4 短预览与整片资源

为局部预览建立明确执行用途和独立的实测资源配置，复用现有媒体编译/受许可执行基础。能力目录、资源声明、调度采样和执行保护共同消费同一配置，不在各层复制预算。

先验证采样器能识别受许可进程组、所有子进程、RSS/线程/IO及退出，再在产品指定M2/16GB目标上测量短预览。暂存文件、修改前后两份媒体、源解码、启动阶段与运行阶段均计入。现有QA组采样新增代码尚未验证，不能直接拿来当标定事实。

资源政策变化与代码搬迁分开提交及验收。阈值只能由实际阶段证据确定；本方案不给出猜测内存值，也不取消全机保护。全机swap拒绝应独立评估其与当前压力/本次增量的关系，先获得证据再沿受权设备策略调整。

### 4.5 三组相互依赖的处理

| 候选 | 处理方式 | 保留 |
| --- | --- | --- |
| sources与source_repository、knowledge_grants | 数据类型/用途规则进入中立内容契约；DDL归数据库迁移；授权服务通过所属仓储公开入口调用 | 当前共享、固定引用、撤权和检索过滤语义 |
| production与avatar_lipsync | 人物、授权和预览记录类型与模型执行分开；仓储不从模型运行模块取得领域类型 | 原授权版本、档案身份与模型选择 |
| 音频/混剪/图层/执行/schema | 执行上下文归媒体运行契约；字体解析提取为图层与字幕真正共用的具体能力；回执类型归中立记录，HTTPschema引用它 | 同一时轴、渲染语义、字体覆盖及许可 |

消除这些不合理依赖的同时保持当前媒体输出，不通过再次增加万能shared模块解决问题。每个共享提取项必须有当前消费者及清楚归属。

### 4.6 视图、助手与启动

Web的任务容器负责当前任务/选择/播放/命令结果协调；阶段组件只读取相应事实与触发动作。服务端业务投影与本地输入、浮层、播放状态分别组织，导航保留会话和草稿。

Pi工具、CLI和GUI沿同一能力目录和请求回执调用。普通HTTP等待结束、工具调用返回、媒体作业完成、用户采用和成片生成分别展示；状态文案通过一个投影/映射消费对应事实。停止对话、取消制作、重试原作业的语义继续分别维护。

API依赖在显式应用创建/生命周期内组装，导入纯业务模块不建数据库、不加载模型、不启动扫描器。生产入口仍只有一个调度驱动；测试可注入最小依赖。现有app.main.app启动方式与打包入口按同批消费者接续，禁止为便于测试创建第二个生产实例。

桌面壳保持原appId、用户目录、设备身份、候选身份和IPC授权；监督API/Web的启动与退出保持既有顺序。结构拆分不要求引入新的独立Worker进程。

## 6. 第一批的具体合同建议

用户结果：在当前任务选第二镜头，将曝光0调整到0.15，得到该镜头修改前后静音预览；未采用前不改草稿，不生成整片，其他镜头、字幕和已经调整的旁白保持。

| 项目 | 约定 |
| --- | --- |
| 当前消费者 | Web画面预览、类型化助手工具、TaskMediaJobs和对应HTTP结果读取 |
| 来源与身份 | 固定任务、基础版本、第二镜头及源修订；保留可信操作者、request/turn身份 |
| 替换路径 | 输入适配 → 预览用例 → 封存候选/执行要求 → 原媒体作业 → 设备许可 → 实际执行/产物登记 → 结果读取 |
| 保存边界 | 预览产物不应用编辑；采用走现有版本事务，正式出片保持明确生成动作 |
| 正向证据 | 实际目标镜头、两份可播放预览、尺寸/时长/音轨范围、输出摘要、源与版本绑定、采用及撤销 |
| 不变证据 | 预览前后任务草稿版本及未选对象保持；采用后未影响音频/字幕；撤销回到原事实 |
| 负向证据 | 执行器无伪造Request/路由反射；未取得许可不运行；过期输入不覆盖；重复请求不重做；原路径不存在 |
| 资源证据 | 同设备固定样本的启动/运行峰值、整个进程组、临时盘与时限，明确失败/未知 |
| 回滚边界 | 原输入与持久化格式不变，回退代码候选；保留已产生产物和记录，不重放未知作业 |

第一批前后分别记录实际耗时、人工操作次数、失败原因及峰值；固定输入重复运行，同时覆盖缓存命中与真实新执行。未实测前不承诺“1秒镜头1秒返回”，不把静音预览当作音频通过。

R1收口后用115.788秒代表任务验收连续两次修改、重新输出、原生保存、撤销/重做和重启回读，验证方法覆盖长任务场景；它与从新目标制作的完整旅程分别留证。

### 7.2 架构检查

实施时增加小而确定的导入/调用检查，检查实际迁移模块：

- 领域、用例和执行模块不依赖app.main或HTTP/UI类型，不调用路由函数。
- 公共契约不引用具体仓储、模型启动或执行器；不能靠把导入移进函数绕过检查。
- SQL写入在所属仓储与明确事务实现中；外围直接私有连接消费者归零。
- 原型、旧API、生成目录和测试替身不进入生产路径。
- 生产初始化仅通过显式组装；重复导入/创建测试应用不启动第二个调度或扫描器。

先冻结现有违例及其负责人；已迁移范围立即严格执行，未迁移范围不能新增同类违例。现有HTTP集成测试仍可导入应用，不能为减少数字删除有价值测试。

### 7.3 完成指标

以覆盖和变化范围衡量，不设全仓文件长度硬上限：

1. 每个活跃业务能力都有一个命令/用例入口、一个计算负责人及明确提交负责人。
2. 所有迁移目标消费者完成接续，旧目标逐项达到RETIRED。
3. main只包含组装、公共边界与生命周期；production不再承担素材分析、模型执行或所有独立资产存储。
4. 纯编辑计算测试不依赖应用、真实数据库或模型；跨对象事务与HTTP/GUI测试仍验证真实边界。
5. 用一个已经批准的小改动演示变化集中在对应能力和必要适配，其他阶段无需补重复规则。
6. 同候选真实制作/改片/保存/重启及数据权限通过；既有不可用能力仍真实表达。

每批分别报告结构完成、功能修复、媒体证据和客户端证据；最后才能报告全面重构验收。整体目标不能被单个修复或一个子包通过替代。

## 10. 所有权、文档和启动方式

主控负责共享文档、契约、派工、审核和集成；产品代码由当批绑定的可见Codex线程、cmux实施者或用户已授权的主控承担。当前不自动恢复任何旧writer或租约。每个巨型文件在拆出阶段只有一个写入负责人，避免多线程同时抽走代码。

API纵向负责人对“用户动作 → 任务/版本 → 作业 → 实际产物 → 旧路径退役”完整负责；Runtime、Web、Desktop、Mobile等负责人在互斥文件内贡献。先冻结共同契约，再并行独立内容；实施与独立审核分开，最终由主控核对同一候选。

批准后的第一份实施合同应包含：R0/R1范围、源候选、具体文件/符号、目标数据与测试环境、明确禁区、真实媒体/客户端许可、同候选验收和退役清单。若批准全面实施，合同按本方案依赖继续R2–R9，不以第一批完成代替整体目标。

稳定的模块/契约变化更新系统架构，对象/状态变化更新领域模型，交互语义变化更新DESIGN，权限变化更新认证边界；本方案只保留分期、候选和迁移工作清单。旧任务合同必须重新绑定，不从历史消息恢复。

当前开发计划的产品范围与R01–R40/E01–E18继续有效；重构批次是实现结构的工作划分，不重编号原需求，也不宣称未验收功能已经完成。

## 11. 最终交付物

- 职责和依赖可核验的源码候选，更新后的活动架构及公共契约。
- 活跃能力/消费者覆盖、旧目标退役和未验证项清单；检查结果绑定候选。
- 定向回归、权限与事务负向检查、真实媒体、客户端和重启证据。
- 固定样本的前后等待、人工操作、峰值资源及失败比较；不编造提升百分比。
- 用户可操作的代表视频与连续改片/保存结果；原生测试包仅在取得对应实施许可后交付。

全面重构接受条件：R0–R9的相关目标完成，所有旧目标RETIRED，权限/数据/版本/恢复保持，核心用户闭环在同一真实候选成立。外部平台、模型或手机能力的独立缺口单列；缺证据不计通过，也不掩盖已完成的结构成果。
