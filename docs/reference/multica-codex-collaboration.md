# Multica 与曜核的协作和能力映射

Multica 是项目控制面，负责任务、依赖、评审、验收证据和阻塞可见性。曜核仓库的产品、领域、架构、设计和代码事实不复制到 Multica，也不由 Multica 保存作品、版本、发布或数据库状态。GitHub 的分支、提交、PR、CI 和真实运行回执仍是实现事实源。

## 能力映射

| Multica 能力组 | 曜核产品纵向切片 | 进入条件 |
| --- | --- | --- |
| M0 权威、需求和项目控制 | 权威文档、GitHub Issue、PR、CI 和验收证据路由 | 规则只有一个文档归属，Multica 只引用 |
| M1 外壳、Project、Session、新建和恢复 | 对话优先的新建、持续 Conversation、空作品区、作品台和恢复 | 新建不再以统一表单为默认入口 |
| M2 公开事件流和对话栏 | 人话说明、真实动作、结果、失败、停止、追加和回读 | 事件来自 Pi/宿主真实回执 |
| M3 Composer、引用、Skill 和 Style | 自然语言、对象引用、按需 Skill 和工作区偏好 | 引用只绑定真实对象、版本和授权 |
| M4 媒体执行和 ffmpeg-skill | Media Execution Layer、JobRun、取消、重试、产物登记和观察 | 未接通能力保持不可运行 |
| M5 实时作品台、预览、时间线和撤销 | 同一作品的当前版本、预览、局部修改、采用和恢复 | UI 读取正式事实源 |
| M6 素材、人物、声音、知识和模板 | 有来源、版本、授权和使用关系的资源库 | 资源目录不等于可执行能力 |
| M7 多 Session、多 Agent、候选和采用 | 同一作品的分支方案、比较、采用、回滚和隔离取消 | 未采用候选不能覆盖正式版本 |
| M8 Provider、模型、用量和诊断 | 真实 Provider 回合、usage、失败分类和诊断 | 没有凭据或真实回执就保持未知 |
| M9 发布、导出、定时和平台适配 | 作品版本发布、账号授权、平台内容编号、数据回查和反馈 | 先完成一个真实平台纵向切片 |
| M10 跨端、恢复和发布质量 | Windows、手机、安装升级、退出恢复、平台质量和生产化 | 各端独立实测，不能互相外推 |

这些组不是曜核内部的固定阶段，也不要求每条创作都经过 M0-M10。它们用于组织项目能力和验收工作，用户路径仍由 Agent 根据目标、证据、授权和实际结果选择当前动作。

## Codex、Multica 和 Agent 的边界

- Codex 负责读取权威文档、修改代码、运行测试和真实验证、创建分支提交和 PR。
- Multica 负责把用户结果拆成可追踪任务，聚合 PR、运行记录、截图、录屏、真实作品和阻塞。
- Multica Agent 可以做需求归类、只读审查、依赖整理和验收草稿。涉及代码写入时必须绑定一个明确的 Codex 任务。
- Pi 是曜核运行时的一部分，负责模型回合、上下文、工具调度和事件，不拥有任务、作品、版本、授权、队列和发布事实。

## 任务记录最小字段

每个实现 Issue 至少链接产品/领域/架构/设计中的权威章节，并写明用户结果、真实入口、事实源、允许修改范围、失败与恢复、验收证据、非目标和关联 PR。Issue 状态不能替代代码、持久化、真实 UI、真实媒体、真实 Provider 或平台回查证据。

## 当前使用规则

Multica 中的任务可以按 M0-M10 组织，但实施顺序以曜核活动合同和 GitHub Issue 为准。发现产品规则变化时先更新曜核权威文档，再更新 Issue 和 Multica 摘要，不能在 Multica 中另立一套产品规则。
