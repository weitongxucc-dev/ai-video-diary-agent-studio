# AI视频日记 Agent 提示词与内容智能升级文档

版本：2026-06-07  
定位：2.0 之后的 Agent 内容能力升级说明  
适用范围：选题生成、口播稿生成、段落重写、反馈学习、发布数据闭环  

## 0. 当前实现状态

截至 2026-06-07，阶段 1 已进入代码实现：

- `Episode.content_template_id` 已传入选题生成、口播稿生成和段落重写。
- DeepSeek 选题 prompt 已包含内容模板、选题结构、标题规则和 `score` 评分 rubric。
- DeepSeek 口播稿 prompt 已包含内容模板、脚本结构、标题/封面/发布规则，并明确 `hook` 是独立字段。
- DeepSeek 段落重写 prompt 已包含内容模板、前后段衔接上下文和目标段落角色。
- `PreferenceSummary` 第一版已实现为 `preference_memory`：active feedback 会聚合成 `prefer` / `avoid` 信号，并进入选题、整篇口播稿和单段重写 prompt。
- 底部指令台已支持 typed / transcribed command 的预览与执行，包括继续流程、重生成选题/口播稿、重写段落、生成草稿、更新剪辑计划片段决策。

仍未实现：

- `Creator Profile`。
- 抖音发布数据和评论洞察闭环。
- 语义检索式长期记忆。
- 真实麦克风录音和本地 ASR 到指令台的接入。

## 1. 核心判断

当前提示词已经达到“工程可用”水平：能稳定让 DeepSeek 返回结构化 JSON，能避免一部分来源幻觉，也能生成基本可用的中文口播稿。

但它还没有达到“产品好用”水平。现在的 Agent 更像一个通用中文口播编导，而不是一个真正懂创作者本人、懂栏目类型、懂历史反馈、懂观众数据的内容搭档。

一句话结论：

```text
当前提示词解决了格式稳定性，下一阶段要解决内容个性化、栏目适配和策略学习。
```

## 2. 当前提示词现状

### 2.1 选题生成

位置：`apps/api/app/topics.py`

当前能力：

- 要求只输出 JSON。
- 要求顶层结构为 `{"topics": [...]}`。
- 要求每个选题包含标题、观点、原因、受众、大纲、评分和来源。
- 要求 `source_refs` 只能来自输入的 `source_items`，不能编造来源。

主要问题：

- `score` 字段没有评分标准，模型会凭感觉打分。
- 没有定义什么是“好选题”。
- 没有要求 4 个选题之间必须显著差异化。
- 没有接入 `content_templates.py` 中已经定义好的栏目结构。
- 素材选择仍以固定类型配额为主，不是按语义相关性和质量排序。

### 2.2 口播稿生成

位置：`apps/api/app/llm.py`

当前能力：

- 要求只输出 JSON。
- 要求包含 `hook`、`sections`、标题候选、封面文案、发布文案和评论引导。
- 强调真人日记感、不要营销腔。
- 禁止动物、怪物、玄幻、热血鸡汤类比。

主要问题：

- 只有“不要营销腔”这类负面约束，缺少创作者本人声音样本。
- 没有使用内容模板中的脚本结构、标题规则、封面规则和发布规则。
- 没有说明 `sections` 与 `topic.outline` 的对应关系。
- `estimated_seconds` 没有估算方法，模型容易随意填。
- 对不同内容类型的节奏差异没有建模，例如视频日记、工具测评、教程演示不应该共用同一套口播结构。

### 2.3 段落重写

位置：`apps/api/app/llm.py`

当前能力：

- 能针对单个 section 重写。
- 会带完整脚本上下文。
- 会带最近反馈事件。

主要问题：

- `recent_feedback` 仍然是最近若干条原始事件，噪声较大。
- 没有过滤与当前段落无关的反馈。
- 没有显式给出前后段落的衔接目标。
- 没有标记目标段落在脚本中的角色，例如背景、核心论证、结尾行动建议。

## 3. 已有能力中最值得保留的部分

这些设计应该继续保留：

- 强制 JSON 输出和字段结构。
- 选题来源约束，禁止编造 `source_refs`。
- 人工复核节点，而不是让 Agent 直接替用户做最终判断。
- 反馈事件可回滚，偏好学习只使用 active evidence。
- `hook` 作为独立字段，`sections` 作为正文段落；不要照搬“sections[0] 是 hook”的外部建议。
- 本地优先，不把用户知识库、视频和密钥默认上传到外部平台。

## 4. 最大问题：Content Template 没有进入生成链路

当前项目已经有内容模板：

- 视频日记：真实经历、冲突问题、个人判断、行动建议。
- AI 工具测评：一句话结论、工具是什么、实测体验、最大问题、是否推荐。
- 教程演示：教程目标、步骤拆分、关键设置、常见错误、最终效果。

但生成选题和口播稿时，模型仍然收到的是通用“AI 视频日记”提示词。

这会导致一个产品错位：

```text
用户在 UI 里选择了栏目，但 Agent 生成时没有真正切换栏目思维。
```

因此，提示词升级的第一优先级不是写更长的 prompt，而是把 `Episode.content_template_id` 对应的模板信息传入 topic/script/section 生成。

## 5. 提示词升级原则

### 5.1 模板优先

每次生成都应该知道当前 Episode 使用哪个内容模板。

Prompt 应包含：

- 模板名称。
- 场景定义。
- 推荐时长。
- 选题结构。
- 脚本结构。
- 标题规则。
- 封面文案规则。
- 发布文案规则。
- 默认反馈维度。

### 5.2 评分必须有 rubric

选题 `score` 不应该让模型自由发挥。

建议评分结构：

```text
真实案例支撑度：30 分
观点鲜明度：30 分
口播转化度：20 分
与近期偏好匹配度：20 分
```

这能减少“看起来都不错，但不知道为什么分高”的问题。

### 5.3 反馈要先摘要，再进入 prompt

不要只把最近 10 条 feedback event 塞给模型。

当前代码已把 active feedback 聚合为 `preference_memory`，格式为：

```json
{
  "prefer": [
    {"signal": "多讲真实项目", "evidence_count": 2, "confidence": 0.65}
  ],
  "avoid": [
    {"signal": "太像概念课", "evidence_count": 1, "confidence": 0.5}
  ]
}
```

后续可以继续增强为更完整的偏好摘要：

- 最近喜欢的方向。
- 最近不喜欢的方向。
- 高频理由。
- 只与当前任务相关的反馈。
- 反馈出现次数。
- 近期程度。

例如：

```json
{
  "preferred": [
    {"reason": "真实案例更强", "count": 3},
    {"reason": "开头判断更直接", "count": 2}
  ],
  "avoided": [
    {"reason": "概念太空", "count": 4},
    {"reason": "太像 AI 文案", "count": 2}
  ]
}
```

### 5.4 创作者人设必须显式建模

“不要营销腔”只能避免一部分错误，但不能让内容像创作者本人。

后续需要建立 Creator Profile：

- 我是谁。
- 我常讲什么领域。
- 我的表达风格。
- 我的禁用词。
- 我喜欢的开头方式。
- 我常用的真实案例类型。
- 我不喜欢的 AI 味表达。
- 3-5 条好脚本样本。
- 3-5 条差脚本样本。

Creator Profile 应该进入所有内容生成 prompt，但要保持短摘要，不能每次塞长文本。

### 5.5 发布表现是参考，不是命令

后续接入抖音数据后，不能让播放数据直接控制 Agent。

正确方式：

```text
播放、点赞、评论数据 -> 生成表现洞察 -> 用户确认 -> 进入偏好记忆 -> 影响下一次生成
```

错误方式：

```text
某条工具测评爆了 -> Agent 以后只推工具测评
```

抖音数据噪声很大，单条爆款不能证明方向正确。Agent 只能从多条内容中提炼模式。

## 6. 推荐的 Prompt 输入结构

### 6.1 选题生成输入

建议结构：

```json
{
  "day_number": 42,
  "content_template": {
    "id": "tool_review",
    "name": "AI 工具测评",
    "scenario": "围绕一个 AI 产品、工具或自动化能力做实测判断。",
    "recommended_duration": "60-180 秒",
    "topic_structure": ["一句话结论", "工具是什么", "实测体验", "最大问题", "是否推荐"],
    "title_rules": ["工具名必须出现", "体现结果或坑点", "避免纯介绍"]
  },
  "creator_profile_summary": {
    "voice": "技术型个人创作者，表达直接，重真实体验和方法复盘。",
    "avoid": ["营销腔", "空泛概念", "过度鸡汤", "网络套话"]
  },
  "source_items": [],
  "preference_summary": {},
  "performance_insights": {},
  "requirements": []
}
```

### 6.2 口播稿生成输入

建议结构：

```json
{
  "day_number": 42,
  "content_template": {},
  "creator_profile_summary": {},
  "topic": {
    "title": "",
    "core_viewpoint": "",
    "outline": [],
    "sources": []
  },
  "preference_summary": {},
  "requirements": [
    "hook 是独立字段，不要放入 sections。",
    "sections 要与 topic.outline 或 content_template.script_structure 对齐。",
    "estimated_seconds 按约 180 字/分钟估算。"
  ]
}
```

### 6.3 段落重写输入

建议结构：

```json
{
  "content_template": {},
  "topic": {},
  "script_context": {
    "hook": "",
    "prev_section_tail": "",
    "next_section_head": ""
  },
  "target_section": {
    "id": "",
    "title": "",
    "role_in_script": "核心论证第 2 段",
    "estimated_seconds": 30,
    "content": ""
  },
  "rewrite_reason": "更像真实经历，少一点概念",
  "relevant_feedback": []
}
```

## 7. 发布数据闭环应该如何进入提示词

后续如果接入抖音数据，不建议一开始追求完全自动采集。

更稳妥的路径：

1. 手动录入或半自动导入播放、点赞、评论、收藏、完播率。
2. 粘贴或导入高赞评论。
3. Agent 生成表现洞察。
4. 用户确认哪些洞察进入偏好记忆。
5. 下一次选题和脚本生成时注入 `performance_insights`。

表现洞察应该长这样：

```json
{
  "sample_size": 12,
  "reliable_patterns": [
    "工具实测类视频平均播放高于个人复盘类，但样本仍偏少。",
    "带真实踩坑经历的开头，评论区更容易出现共鸣反馈。"
  ],
  "audience_requests": [
    "观众多次要求补充具体操作步骤。",
    "观众对工具价格和替代方案敏感。"
  ],
  "do_not_overfit": [
    "单条爆款不作为长期方向依据。",
    "发布时间建议必须结合样本量。"
  ]
}
```

Prompt 中应明确：

```text
表现洞察只作为参考，不要机械追随单条视频数据。优先采用多条视频中重复出现的模式。
```

## 8. 分阶段落地计划

### 阶段 1：模板接入 Prompt

目标：

- 选题生成接收 `content_template`。
- 口播稿生成接收 `content_template`。
- 段落重写接收 `content_template`。
- 不改变现有页面交互。

验收标准：

- 选择“AI 工具测评”后，生成结果必须包含工具名、实测体验、坑点和推荐边界。
- 选择“教程演示”后，生成结果必须包含步骤结构、常见错误和最终效果。
- 选择“视频日记”后，继续保持真实经历和个人判断风格。

### 阶段 2：选题评分 rubric

目标：

- System prompt 中加入选题质量标准。
- User prompt 中加入差异化要求。
- 返回结果中的 `score` 更可解释。

验收标准：

- 4 个选题不得只是标题不同、观点相近。
- 每个选题至少说明一个真实素材支撑点。
- 低素材支撑的选题分数必须低于强素材支撑的选题。

### 阶段 3：反馈摘要

目标：

- 增加 `PreferenceSummary` 或类似结构。
- 生成 prompt 不再直接吃最近 10 条原始 feedback。
- 段落重写只接收相关反馈。

验收标准：

- 高频 down reason 能被聚合为“避免方向”。
- 段落重写不会被无关段落反馈误导。
- 反馈撤销后不再进入摘要。

### 阶段 4：Creator Profile

目标：

- 建立创作者声音画像。
- 支持维护禁用词、偏好表达、好样本、差样本。
- 所有内容生成都接收短版 creator profile。

验收标准：

- 生成稿的“AI 味”显著减少。
- 用户手动修改比例下降。
- 用户能在 UI 中查看和编辑 Creator Profile。

### 阶段 5：发布数据与评论洞察

目标：

- 手动录入或导入发布表现数据。
- 粘贴/导入评论。
- Agent 生成“表现洞察”和“观众信号”。
- 用户确认后进入下一次生成。

验收标准：

- 系统能区分“数字表现”和“评论信号”。
- 样本量不足时不会输出武断结论。
- 只有用户确认过的洞察才进入生成 prompt。

## 9. 不建议直接做的事情

短期不建议：

- 直接把外部建议里的长 prompt 全部复制进代码。
- 让播放量自动决定下一次选题。
- 让 Agent 自动跳过所有人工审核。
- 在没有样本量的情况下做“爆款归因”。
- 把 `hook` 合并进 `sections`，这会破坏当前数据结构。
- 为了“更像 Agent”而让工作流变得不可解释。

## 10. 成功标准

提示词升级是否成功，不看 prompt 写得多长，而看用户实际修改量是否下降。

建议用这些指标评估：

- 选题通过率：4 个候选里，用户愿意确认的比例。
- 脚本保留率：生成稿中用户不修改直接保留的段落比例。
- 段落重写命中率：用户重写一次后是否满意。
- 模板命中率：工具测评、教程演示是否真的生成了不同结构。
- 偏好生效率：用户反馈后，后续生成是否能明显避开同类问题。
- 发布洞察有效率：用户确认过的表现洞察是否能转化为下一次选题或脚本改进。

## 11. 下一步建议

最应该先做的是：

```text
Content Template -> Prompt Context -> Topic/Script Generation
```

这一步 ROI 最高，因为它会让 2.0 已经做好的“内容模板选择”真正影响 Agent 生成结果。

之后再做：

```text
FeedbackEvent -> PreferenceSummary -> Prompt Context
```

最后再做：

```text
Published Metrics + Comments -> Performance Insights -> User-confirmed Memory
```

这样产品会从“通用内容生成工具”逐步升级为“懂我、懂栏目、懂观众反馈的个人内容 Agent”。
