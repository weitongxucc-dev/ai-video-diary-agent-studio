# 开发、并行代理与验收流程

状态：工程执行权威
职责：复杂任务按什么粒度拆分、如何并行、由谁审核以及运行哪些验证。简单任务只遵循根 AGENTS.md，不必加载本文。

## 1. 先分级，再决定是否并行

| 级别 | 判断标准 | 默认执行方式 |
| --- | --- | --- |
| S0 只读或微小 | 解释、审查、定位、文案、单点配置；没有实现或只有极小可逆修改 | 主线程直接完成，不建长计划，不开子线程 |
| S1 单领域 | 一个模块、一个用户结果、文件边界集中 | 被指派的实施线程实现，按第7节选择最小必要证据 |
| S2 可并行功能 | 两个以上可独立验收的工作包，文件所有权不重叠，协调成本明显小于串行成本 | 主控规划，可见实施线程按独占范围并行，主控审核集成 |
| S3 高风险 | 实质改变产品权威、安全／数据边界、持久化数据、默认业务入口、发布，或不可逆动作 | 主线程先冻结权威、风险和验收；只把边界明确的调查或实现并行 |

任务大不等于应该并行。以下情况保持单线程：

- 后一步必须等待前一步的设计结论；
- 多个工作包会修改同一个核心文件或状态机；
- 主要难点是一个高耦合问题，而不是多个独立问题；
- 单个 Agent 能在协调完成前直接做完；
- 需求仍未冻结，派工会让多个线程重复猜测。

## 2. 主线程职责

主线程始终是唯一调度和验收负责人：

1. 解释用户目标、明确非目标和授权范围。
2. 读取所需权威文档，解决冲突；不能把权威解释整体外包。
3. 为每个工作包定义目标、拥有文件、依赖、禁止范围和可观察验收。
4. 保证同时写入的文件集合互斥；自己不与子线程并行修改同一文件。
5. 处理跨模块接口、共享状态机和产品命名。
6. 逐个阅读子线程 diff 和风险对应的验证证据，不把“子线程说完成”当验收。
7. 只在合并后运行一次必要的集成检查，避免每个线程重复全量构建。
8. 给用户报告最终结果、验证范围、未验证项和剩余风险。

主线程不应该只派工后等待，也不应该在子线程工作期间重复做同一份实现。

## 3. 子线程任务契约

每个派工消息必须包含：

    目标：
    用户可见或契约级验收：
    要求的证据等级：
    Owned files：
    权威绑定（直接相关章节＋基线；确有失效检测需求时才生成机器快照）：
    不得修改：
    本次风险与最小验证（可复用的证据、确需执行的命令或实际操作）：
    回报：改动、验证结果、未覆盖风险、阻断

迁移或替换任务还必须包含：迁移负责人、旧目标及当前消费者、新权威与替代路径、正向验收、负向验收、删除条件、允许共存的截止条件、真实目标证据和不存在证明。只描述“新增什么”的契约无效。

禁止派发“研究整个仓库”“把相关问题都修了”“再读一遍所有文档”之类无边界任务。派工绑定要证明的行为和风险，不预设必须新增测试文件；测试是否新增、删改或复用沿[AGENTS第6节](../AGENTS.md#6-完成与验收)判断。需要修改的既有测试也须明确唯一写入者；共享测试文件有冲突时串行交接，不为并行另复制一套。

子线程必须：

- 只修改 owned files，不顺手修无关问题；
- 发现共享契约变化时先通知主线程，不自行扩张；
- 收到权威暂停通知后在安全边界停止，保留当前 diff，不用旧任务契约继续工作；
- 收到新权威后重读指定章节，评估已有改动并完成 `REBASE_ACK`；
- 不创建下级代理，除非主线程明确授权；
- 不执行 push、发布、迁移、删除或外部写操作，除非任务契约明确授权；
- 用精确路径、实际验证方法和结果回报；复用证据须说明为何仍适用，不复制大段日志。

### 3.1 短期活动合同

S2/S3 工作需要跨对话恢复、分配给多个线程或执行迁移退役时，可以使用仓库根目录的 `.project-control/active-contract.md` 保存唯一活动合同。只有用户要求继续当前复杂任务、主线程明确派工或合同被点名时才读取；普通任务不扫描该目录。

活动合同绑定当前基线、目标与非目标、负责人及独占文件、直接相关权威、事实源、接受条件和授权范围；迁移任务再记录旧目标及删除条件，实际存在阻断时才记录阻断。它可以记录带日期的当前证据，但不能覆盖 AGENTS.md 的工程纪律，也不能改写产品、领域、设计或安全权威。

同一时间只保留一份活动合同。按工作包绑定相关章节；有语义影响的变化只使受影响绑定失效，不因其他工作包、进度或格式变化暂停整轮。目标仍成立的局部调整原位修订；目标或主要方案失效才替换任务。文件交接直接更新所有权表并移除旧分工，不在末尾追加“补绑/接回”覆盖前文；已结束、暂停撤权或被替代的源码绑定退出当前表，历史由 Git 保留。主线程通知受影响线程，不保留并列旧副本。达到 `MIGRATION_ACCEPTED`、任务取消或合同被外部 Issue/PR 完整接管后删除该文件，由 Git 保存历史，不移入 `docs/archive/`。

## 4. 推荐拆分方式

优先按可以独立验收的纵向或边界工作包拆分：

- Web 可见流程 / API 契约与领域实现 / Worker 或媒体实现；
- 来源连接器 / 模型能力 / 发布平台适配器；
- 高风险边界的实现 / 必要的独立安全或集成审查；普通改动不默认拆出测试线程；
- arm64 与 x64 构建调查，但最终发布仍由主线程统一门禁。

不推荐：

- 按“组件、CSS、测试”拆同一个小页面，导致三方反复协调；
- 多个线程同时修改 main.py、共享 schema、同一 migration 或同一设计权威；
- 一个线程写功能，另一个线程在功能未冻结前写大量测试假设；
- 让每个线程各跑一遍全量 Web、API 和打包。

### 4.1 产品级迁移与退役

AI 默认倾向增加覆盖层而不证明旧路径可退出。是否使用 Migrate 按根 AGENTS.md 的实际影响边界判断，不因 replace、delete 等词自动升级。范围内且消费者明确的局部源码清理或组件替换按 S1/S2 处理；风险分级不替代删除授权，子线程仍遵守显式 owned files 与禁止事项。

文件可以按技术边界互斥分配，但验收责任必须围绕一个用户闭环集中给迁移负责人：

    用户目标 -> 真实页面 -> 唯一事实源 -> 授权边界
    -> 真实动作 -> 持久化结果 -> 真实产物
    -> 旧路径删除 -> 不存在证明

迁移状态为：

    LEGACY_INVENTORIED
      -> NEW_AUTHORITY_FROZEN
      -> VERTICAL_SLICE_IMPLEMENTED
      -> REAL_TARGET_VERIFIED
      -> OLD_PATH_DISABLED
      -> OLD_PATH_REMOVED
      -> ABSENCE_VERIFIED
      -> MIGRATION_ACCEPTED

单个退役目标只使用 `ACTIVE -> COEXISTING -> MIGRATED -> RETIRED`。只有 `RETIRED` 算完成。按实际范围在现有线程、Issue/PR 或临时证据中记录旧目标退役、替代能力和真实交互证据；可合并记录，不强制维护三张重复矩阵。临时记录波次结束后清除，必要原始证据保留，不进入活动权威文档。

负向验收至少按目标选择以下证据：活动消费者归零或剩余命中被分类；旧路由不可达；旧事实源不可写；原始路径和旧授权标识被拒绝；旧依赖/样式不进入构建；同一真实候选中旧控件和名称不可见；保护错误产品行为的测试已删除或改写；删除旧文件后仍能干净构建和运行。

不得混淆证据等级：

    STATIC_WIRING_CONFIRMED
    RUNTIME_CALL_CONFIRMED
    REAL_INTERACTION_CONFIRMED
    PERSISTED_EFFECT_CONFIRMED
    REAL_OUTPUT_CONFIRMED
    END_TO_END_ACCEPTED

前一等级不蕴含后一等级。真实客户端测试开始前先验证权限、窗口聚焦、一个无害点击、一个键盘探针和隔离数据；第零探针失败暂停该验证路线，不继续累积未执行案例。其余独立的已授权工作可继续；所需客户端证据缺失时不得宣布客户端验收通过。

## 7. 最小验证矩阵

按[AGENTS第4、6节](../AGENTS.md)执行验证节制。下表是按风险选择的入口，不是每次必须叠加的检查清单，也不要求新增测试。先检查既有覆盖与可复用证据，再选择能直接发现本次错误的最小验证；真实用户结果所需的证据等级不能降低。

| 改动 | 优先验证入口 | 何时补充验证 |
| --- | --- | --- |
| 文档 | 相对链接、残留引用、权威重复；变更 DESIGN.md 时才做 design-md 检查 | 文档改变产品或安全契约时审查相关实现 |
| Web 组件或页面 | 真实页面可见验收；纯文案/样式修改不新增单测 | 交互或状态逻辑变化时选择对应已有用例；共享组件检查受影响消费者，不自动跑全部 Web 测试 |
| API 领域逻辑 | 最接近变更行为的已有用例或可复现实证 | 现有证据不能覆盖真实故障/不变量时补最小用例；跨模块影响扩大到实际消费者 |
| Web + API 契约 | 一条经过实际消费者的请求/页面链路，检查真实字段和效果 | 链路未覆盖的解析、拒绝或兼容风险才补对应层验证，不默认双侧另写一套 |
| Worker、媒体或模型 | 故障定位选择直接用例或小样本；成片、模型行为及性能结论必须来自相应真实运行 | 持久化、取消、恢复或资源边界变化时补该风险的证据，不固定叠加单测与 smoke |
| Electron | 按影响选择目标脚本、实际桌面操作或打包 smoke | 只有包环境、进程、路径、架构或分发风险需要时按 desktop 文档升级 |
| 认证和 workspace | 按安全权威验证本次受影响的负向边界和实际双用户隔离；复用仍适用的已有入口 | 登录、session、onboarding或分发路径受影响时检查对应完整流程 |
| 发布 | 本次 connector/授权/失败语义对应的已有用例或实际草稿流程 | 真正签名、分发或发布时执行适用的 RELEASE 和 workflow 门禁 |

补充验证须指出已有证据未覆盖的具体风险；同一条有效证据可满足多个接受点，不为不同线程重复执行。测试通过后，没有新改动、失败或未解决风险就停止扩测；真实链路失败先定位首个具体失败，不以增加局部断言或重跑全量代替诊断。真实操作无法证明的安全、事务和恢复边界仍须取得对应证据，不能用一次成功演示替代。

UI 按[DESIGN尺寸与状态验收](../DESIGN.md#61-尺寸与状态)选择适用页面、代表尺寸和最小窗口，实际验证可见行为。截图只证明当时可见结果，不能替代数据或安全测试。

迁移验收必须使用同一候选同时证明新路径成立和旧路径不存在。静态连线、mock、单测、构建或进程启动不能提升为功能或端到端 PASS；环境阻断只能记录为 BLOCKED，未执行项保持未知。

跨入口纵向工作另核GUI、Pi、CLI、MCP/消息适配是否调用同一具体用例与schema，未知请求有持久查询回执，不由客户端或协议层另存完成状态。原生工具验证真实文件/进程执行边界和产物登记；专业编辑验证帧/声音、撤销及输出。提示词/schema/Skill修改用同一实际粗剪、多轮精修和恢复样本比较，不能用工具数量或静态提示检查代替结果。检索变更固定正反例与来源，不以返回数量验收。

## 8. 审核顺序

主线程按以下顺序收口：

1. 范围：diff 是否只实现用户要求，是否误改用户现有工作。
2. 权威：产品名词、设计、领域和接口是否一致。
3. 失败语义：是否存在吞错、伪造成功、过宽回退或无法恢复状态。
4. 数据与安全：workspace、授权、本地路径、秘密和外部发送范围。
5. 可见体验：普通用户能否理解当前状态、下一步和影响。
6. 验证：证据是否覆盖本次风险；新增测试有何独有价值，能否复用已有入口；重复或过期断言是否应在本次范围内删改。不得以数量、比例或文件交付代替效果。
7. 清理：迁移完成后是否删除旧入口、旧文案和临时文件。

## 9. 局部阻断与请求决定

先暂停受影响动作，不自动停止全部工作。主控可解决的路由、已授权实现或测试入口问题由主控处理；无法在既有授权内解决以下事项时，提供证据、影响和所需最小决定：

- 当前权威冲突，且无法依据明确用户决定或既定归属解决；
- 用户脏改与目标文件重叠，无法安全保留；
- 需要新的外部权限、秘密、付费服务或平台账号；
- 需要未经明确授权的数据迁移、发布、删除或不可逆操作；
- 对重复失败做过定向原因核查后，仍无安全且有证据支持的下一步；
- 验收需要真实设备、账号或外部状态，当前无法获得。

阻断项保持 BLOCKED／未知，独立工作继续；只有整个剩余目标依赖缺失条件时才整体交回。停止不等于添加绕行层，继续也不等于降低验收、安全或用户批准要求。阶段实现完成、验证完成、最终迁移验收分别报告。

## 10. 文档治理

- 文档变更遵循 docs/README.md 的唯一权威和生命周期规则。
- 产品或架构决策如果尚未落入权威，不应先实现再依赖聊天记录解释。
- 只在出现跨模块、难逆转且存在真实备选方案的决定时创建 ADR；不预建空目录。
- 不新增与 PRD、活动合同并列的阶段计划、完成清单或实时任务看板。长期演进顺序与用户结果归 PRD；下一阶段的工作包、依赖、边界和剩余验收归第 3.1 节的唯一短期活动合同，允许跨对话维护，结束后清除。普通旧版本由 Git 追溯；`docs/archive/` 只隔离无法由 Git 重建且必须留存的历史证据，并默认禁止 Agent 读取。

## 11. ACT 动态权威变更协议

ACT 用于让受影响任务及时接收新的权威。通用 C0–C3 分级、批准检查、暂停、变更消息和重新绑定由已安装的 `$project-authority-harness` Change 模式及其 `references/change-transaction.md` 维护；本文不保留第二套状态机和消息模板。

本项目执行约束：

- 只有相关语义变化才使绑定失效。已批准功能尚未实现属于工作内容，不因“缺少能力”自动重开需求；跨模块新增含义仍由主控审查。
- 项目显式授权和批准门禁优先于 Skill；用户已明确批准的同一事项无需重复批准，逐次批准要求不变。新增费用、供应商、数据接收方、数据范围或权限超出原批准时仍须用户决定；凭据存在不是调用授权。
- 主控是并行期间唯一共享权威写入者。C0 在原范围实现，C1 修改受影响合同条款；C2/C3 仅暂停受影响写入，完成文档检查和语义 ACK 后由主控确认恢复。主控可以在恢复消息中预先写明 ACK 满足后的继续条件，不必再往返一次 START；明确保留的 HOLD 不自行解除。
- 局部文件交接不重开整轮：原负责人停写并交接 diff，主控更新归属，新负责人确认后接手。子线程不得自行扩展 owned files。
- 目标、核心语义或主要方案失效时才替换任务；新任务只接收当前权威、必要代码状态和可复用证据，不继承失效长对话。
- 文档事务按 docs/README.md 生命周期处理旧规则和引用；不得将事务当成新的删除、发布、付费或外发授权。保留用户脏改与不可重建证据。
- 阻断与完成遵循第 9 节；治理事务完成不代表用户目标完成，继续剩余已授权实现与验证。只对受影响范围重新评估，不重复全量测试。
