# 开发、并行代理与验收流程

状态：工程执行权威
职责：复杂任务按什么粒度拆分、如何并行、由谁审核以及运行哪些验证。简单任务只遵循根 AGENTS.md，不必加载本文。

## 1. 先分级，再决定是否并行

| 级别 | 判断标准 | 默认执行方式 |
| --- | --- | --- |
| S0 只读或微小 | 解释、审查、定位、文案、单点配置；没有实现或只有极小可逆修改 | 主线程直接完成，不建长计划，不开子线程 |
| S1 单领域 | 一个模块、一个用户结果、文件边界集中 | 主线程实现，最小相关测试 |
| S2 可并行功能 | 两个以上可独立验收的工作包，文件所有权不重叠，协调成本明显小于串行成本 | 主线程规划，2–3 个子线程并行，主线程审核集成 |
| S3 高风险 | 产品权威、安全、认证、迁移、发布、签名、数据删除或跨工作区 | 主线程先冻结权威、风险和验收；只把边界明确的调查或实现并行 |

任务大不等于应该并行。以下情况保持单线程：

- 后一步必须等待前一步的设计结论；
- 多个工作包会修改同一个核心文件或状态机；
- 主要难点是一个高耦合问题，而不是多个独立问题；
- 单个 Agent 能在协调完成前直接做完；
- 需求仍未冻结，派工会让多个线程重复猜测。

## 2. 主线程职责

主线程始终是唯一调度和验收负责人：

1. 解释用户目标、明确非目标和授权范围。
2. 读取所需权威文档，解决冲突；不能把权威解释整体外包。
3. 为每个工作包定义目标、拥有文件、依赖、禁止范围和可观察验收。
4. 保证同时写入的文件集合互斥；自己不与子线程并行修改同一文件。
5. 处理跨模块接口、共享状态机和产品命名。
6. 逐个阅读子线程 diff 和测试证据，不把“子线程说完成”当验收。
7. 只在合并后运行一次必要的集成检查，避免每个线程重复全量构建。
8. 给用户报告最终结果、验证范围、未验证项和剩余风险。

主线程不应该只派工后等待，也不应该在子线程工作期间重复做同一份实现。

## 3. 子线程任务契约

每个派工消息必须包含：

    目标：
    用户可见或契约级验收：
    要求的证据等级：
    Owned files：
    Authority Snapshot（S2/S3：最多 1–2 份文档的具体章节和基线）：
    不得修改：
    最小验证命令：
    回报：改动、测试、风险、阻断

迁移或替换任务还必须包含：迁移负责人、旧目标及当前消费者、新权威与替代路径、正向验收、负向验收、删除条件、允许共存的截止条件、真实目标证据和不存在证明。只描述“新增什么”的契约无效。

禁止派发“研究整个仓库”“把相关问题都修了”“再读一遍所有文档”之类无边界任务。

子线程必须：

- 只修改 owned files，不顺手修无关问题；
- 发现共享契约变化时先通知主线程，不自行扩张；
- 收到权威暂停通知后在安全边界停止，保留当前 diff，不用旧任务契约继续工作；
- 收到新权威后重读指定章节，评估已有改动并完成 `REBASE_ACK`；
- 不创建下级代理，除非主线程明确授权；
- 不执行 push、发布、迁移、删除或外部写操作，除非任务契约明确授权；
- 用精确路径、测试命令和失败证据回报，不复制大段日志。

### 3.1 短期活动合同

S2/S3 工作需要跨对话恢复、分配给多个线程或执行迁移退役时，可以使用仓库根目录的 `.project-control/active-contract.md` 保存唯一活动合同。只有用户要求继续当前复杂任务、主线程明确派工或合同被点名时才读取；普通任务不扫描该目录。

活动合同必须绑定实现基线、目标与非目标、纵向负责人、直接相关权威章节、事实源、真实验收、旧目标、删除条件、阻断和授权范围。它可以记录带日期的当前证据，但不能改写产品、领域、设计或安全权威。

同一时间只保留一份活动合同。范围、对象、事实源或验收发生变化时原合同立即失效，主线程直接替换文件内容并通知受影响线程重新绑定；不把旧副本并排保存。达到 `MIGRATION_ACCEPTED`、任务取消或合同被外部 Issue/PR 完整接管后删除该文件，由 Git 保存历史，不移入 `docs/archive/`。

## 4. 推荐拆分方式

优先按可以独立验收的纵向或边界工作包拆分：

- Web 可见流程 / API 契约与领域实现 / Worker 或媒体实现；
- 来源连接器 / 模型能力 / 发布平台适配器；
- 实现 / 独立测试或安全审查；
- arm64 与 x64 构建调查，但最终发布仍由主线程统一门禁。

不推荐：

- 按“组件、CSS、测试”拆同一个小页面，导致三方反复协调；
- 多个线程同时修改 main.py、共享 schema、同一 migration 或同一设计权威；
- 一个线程写功能，另一个线程在功能未冻结前写大量测试假设；
- 让每个线程各跑一遍全量 Web、API 和打包。

### 4.1 产品级迁移与退役

AI 默认倾向增加覆盖层、adapter、兼容路由和 fallback，而不主动证明旧路径可以删除。涉及 redesign、modernize、consolidate、migrate、replace、deprecate 或统一事实源时，使用 `$project-authority-harness` 的 Migrate 模式，并按 S3 管理。

文件可以按技术边界互斥分配，但验收责任必须围绕一个用户闭环集中给迁移负责人：

    用户目标 -> 真实页面 -> 唯一事实源 -> 授权边界
    -> 真实动作 -> 持久化结果 -> 真实产物
    -> 旧路径删除 -> 不存在证明

迁移状态为：

    LEGACY_INVENTORIED
      -> NEW_AUTHORITY_FROZEN
      -> VERTICAL_SLICE_IMPLEMENTED
      -> REAL_TARGET_VERIFIED
      -> OLD_PATH_DISABLED
      -> OLD_PATH_REMOVED
      -> ABSENCE_VERIFIED
      -> MIGRATION_ACCEPTED

单个退役目标只使用 `ACTIVE -> COEXISTING -> MIGRATED -> RETIRED`。只有 `RETIRED` 算完成。临时维护三张控制矩阵：旧系统退役矩阵、能力真实性矩阵、真实交互证据矩阵；它们放在线程、Issue/PR 或临时证据目录，波次结束后删除，不进入活动权威文档。

负向验收至少按目标选择以下证据：活动消费者归零或剩余命中被分类；旧路由不可达；旧事实源不可写；原始路径和旧授权标识被拒绝；旧依赖/样式不进入构建；同一真实候选中旧控件和名称不可见；保护错误产品行为的测试已删除或改写；删除旧文件后仍能干净构建和运行。

不得混淆证据等级：

    STATIC_WIRING_CONFIRMED
    RUNTIME_CALL_CONFIRMED
    REAL_INTERACTION_CONFIRMED
    PERSISTED_EFFECT_CONFIRMED
    REAL_OUTPUT_CONFIRMED
    END_TO_END_ACCEPTED

前一等级不蕴含后一等级。真实客户端测试开始前先验证权限、窗口聚焦、一个无害点击、一个键盘探针和隔离数据；第零探针失败立即 HOLD，不继续累积未执行案例。

## 5. Token 与上下文预算

### 5.1 查找

- 先用 rg --files 确认候选文件，再用 rg 搜索符号、路由或标题。
- 读取命中附近和直接依赖；只有出现缺口才扩大一层。
- 默认排除 node_modules、build、dist、缓存、媒体和生成产物。
- Git 历史只在追溯回归、权威来源或用户明确要求时读取。

### 5.2 工具输出

- 每条命令限制路径和输出行数；大日志先搜索失败标识，再读取上下文。
- 不把同一文件通过多个命令重复完整输出。
- 测试通过只报告命令和结果摘要；失败保留首个真实失败和必要上下文。
- 连续两次得到同一根因后停止增加猜测式检查，回到契约或请求决策。

### 5.3 沟通

- 进度更新只包含新发现、当前决定和实际阻断。
- 不重复用户原话、计划全文、子线程回报全文或已经可见的工具输出。
- Agent handoff 使用任务消息或 PR，不在仓库长期维护不断过期的状态文件。

## 6. 避免防御性编程

防御只放在真实信任边界：

- 用户输入、上传文件和外部链接；
- 身份、workspace 和权限；
- 文件系统、移动硬盘和路径授权；
- 网络、模型供应商、信息源和发布平台；
- 数据库存取、进程启动、ffmpeg 和模型输出。

内部已经通过边界验证的数据使用明确类型和不变量。禁止：

- 为理论上的未来格式增加多层兼容解析；
- 在每层重复同一校验；
- 宽泛捕获 Exception 后返回空列表、默认成功或旧结果；
- 用静默本地回退掩盖云端、授权或连接错误；
- 没有当前调用方的通用工厂、包装器、配置开关和缓存层；
- 为了避免测试失败而降低契约或跳过关键断言。

允许的重试必须同时满足：外部或进程边界、操作幂等、次数有界、每次尝试可追溯。其他错误明确失败并保留恢复点。

## 7. 最小验证矩阵

先按改动选择最小集合；只有共享契约或风险扩大时升级：

| 改动 | 最小验证 | 何时升级 |
| --- | --- | --- |
| 文档 | 相对链接、残留引用、权威重复、design-md 检查 | 文档改变产品或安全契约时审查相关实现 |
| Web 组件或页面 | 目标单测/契约检查 + 真实页面可见验收 | 共享组件或路由变化时运行 Web 测试和构建 |
| API 领域逻辑 | 目标 pytest 文件或测试名 | schema、repository 或跨模块契约变化时扩大 API 测试 |
| Web + API 契约 | 双侧目标测试 + 一个真实请求/页面流程 | 影响通用客户端时运行 Web contract |
| Worker、媒体或模型 | 目标单测 + 一个小 fixture 或 smoke | 任务状态/恢复变化时加 API/Worker 集成 |
| Electron | 目标脚本或打包 smoke | 进程、路径、架构或分发变化时按 desktop 文档升级 |
| 认证和 workspace | 安全文档对应负向测试和双用户隔离 | 分发包时跑完整登录、session、onboarding |
| 发布 | connector 测试、草稿/确认门和失败语义 | 真实交付时执行 RELEASE 和 workflow 全部门禁 |

UI 必须在 1024×768、1180×800、1440×900 的适用页面验证可见行为。截图只证明当时可见结果，不能替代数据或安全测试。

迁移验收必须使用同一候选同时证明新路径成立和旧路径不存在。静态连线、mock、单测、构建或进程启动不能提升为功能或端到端 PASS；环境阻断只能记录为 BLOCKED，未执行项保持未知。

## 8. 审核顺序

主线程按以下顺序收口：

1. 范围：diff 是否只实现用户要求，是否误改用户现有工作。
2. 权威：产品名词、设计、领域和接口是否一致。
3. 失败语义：是否存在吞错、伪造成功、过宽回退或无法恢复状态。
4. 数据与安全：workspace、授权、本地路径、秘密和外部发送范围。
5. 可见体验：普通用户能否理解当前状态、下一步和影响。
6. 测试：证据是否覆盖改动风险，是否只是数量好看。
7. 清理：迁移完成后是否删除旧入口、旧文案和临时文件。

## 9. 停止并请求决定

出现以下情况时停止扩张实现，提供证据、影响和所需决定：

- 两份当前权威文档直接冲突；
- 用户脏改与目标文件重叠，无法安全保留；
- 需要新的外部权限、秘密、付费服务或平台账号；
- 需要未经明确授权的数据迁移、发布、删除或不可逆操作；
- 同一根因连续两次失败，继续尝试只会增加猜测；
- 验收需要真实设备、账号或外部状态，当前无法获得。

停止不等于添加绕行层。不得为了继续推进而降低安全、隐藏失败或发明第二套状态。

## 10. 文档治理

- 文档变更遵循 docs/README.md 的唯一权威和生命周期规则。
- 产品或架构决策如果尚未落入权威，不应先实现再依赖聊天记录解释。
- 只在出现跨模块、难逆转且存在真实备选方案的决定时创建 ADR；不预建空目录。
- 不维护阶段计划、完成清单或实时任务看板。普通旧版本由 Git 追溯；`docs/archive/` 只隔离无法由 Git 重建且必须留存的历史证据，并默认禁止 Agent 读取。

## 11. ACT 动态权威变更协议

ACT（Authority Change Transaction）用于处理执行期间出现的设计漏洞、新需求、不可实现条件或共享契约调整。它解决的是“文件已经变了，但活动线程仍依据旧上下文继续工作”的问题。

### 11.1 变化来源与分级

变化可以来自用户、主线程、子线程、外部平台、模型能力或运行约束。主线程按影响分级：

| 级别 | 判断标准 | 默认处理 |
| --- | --- | --- |
| C0 局部实现 | 不改变其他模块的调用、用户结果或稳定规则 | 由拥有线程在任务范围内调整，不更新权威 |
| C1 单任务契约 | 改变一个任务的方案或验收，但不影响共享对象和接口 | 主线程替换该任务契约，只通知该线程 |
| C2 共享权威 | 改变对象、状态、命名、API、跨模块数据流或共同验收 | 暂停受影响线程，更新唯一权威，定向重新绑定 |
| C3 产品或高风险 | 改变产品范围、主流程、安全、数据归属、发布方式、外部付费能力或大量既有工作 | 立即暂停相关工作，用户确认，完成权威事务；必要时使用新线程和新波次 |

当分级不确定时，按较高一级先暂停受影响部分；暂停范围必须来自任务的 Authority Snapshot 和文件依赖，不能无差别停止所有线程。

### 11.2 状态机

    RUNNING
      -> CHANGE_DETECTED
      -> IMPACT_ASSESSED
      -> AFFECTED_HELD（仅 C2/C3）
      -> USER_CONFIRMED（需要时）
      -> AUTHORITY_UPDATED
      -> OBSOLETE_CONTENT_RETIRED
      -> DOCS_VALIDATED
      -> REBIND_SENT
      -> REBASE_ACKNOWLEDGED
      -> RESUMED 或 REPLACED

任何 C2/C3 变化都不能从 `CHANGE_DETECTED` 直接跳到继续实现。没有完成文档验证和重新绑定，旧任务契约保持失效状态。

### 11.3 变更提案

子线程发现旧设计有误或现实条件不具备时，发送精简提案，不直接修改共享权威：

    CHANGE_PROPOSAL
    来源：用户 / 主线程 / 子线程 / 外部条件
    当前权威：文件#章节
    证据：可复现事实或真实限制
    建议：旧规则 -> 新规则
    影响：产品 / 领域 / UI / API / Worker / Electron
    受影响任务和文件：
    现有改动：可保留 / 需调整 / 可能废弃
    是否阻断当前任务：是 / 否

主线程负责区分实现误解与权威缺陷、确定规则归属、影响线程和是否需要用户确认。没有改变稳定语义的局部问题不得升级成文档重写。

### 11.4 定向暂停

确认 C2/C3 后，主线程先发送：

    HOLD_FOR_AUTHORITY_UPDATE
    原因：
    失效的任务契约或权威章节：
    立即动作：结束当前不可中断操作；停止新增修改；保留并回报当前 diff
    禁止：基于旧规则继续扩张，或让其他线程接管同一文件

不受变更影响的任务继续执行。子线程在暂停期间只允许回报现状、风险和可保留改动，不运行新的实现或大范围测试。

### 11.5 权威事务与旧内容退役

并行波次中只有主线程可以写共享权威。主线程在暂停窗口内一次完成：

1. 修改真正拥有规则的活动文档；
2. 仅在其他权威中更新其各自负责的产品、领域、架构、设计或安全部分，不复制同一规则；
3. 删除活动文档中的旧表述、旧名称和旧路径；
4. 被整体替代的普通文档直接删除，由 Git 保存历史；确需留存的证据按 `docs/archive/README.md` 移入隔离区；
5. 检查相对链接、残留引用、重复权威、术语和受影响代码契约；
6. 以 Git commit、工作树文件 hash 或明确的任务契约版本标识新基线。

活动文档更新完成前不发送恢复通知。新旧规则不得长期并列，也不得让子线程自行选择使用哪个版本。

### 11.6 重新绑定

文档验证后，主线程向受影响线程发送：

    AUTHORITY_CHANGED
    变更编号：
    旧任务契约：已失效
    新任务契约：
    必须重读：文件#章节
    核心变化：旧规则 -> 新规则
    现有代码处理：保留 / 调整 / 废弃 / 待评估
    恢复前回报：兼容性、受影响文件、新计划和新基线

子线程必须返回：

    REBASE_ACK
    新任务契约版本：
    已重读章节：
    现有改动：可保留 / 需修改 / 应废弃
    受影响文件：
    下一步：

轻微 C1 变化可以在同一线程用替换任务契约继续。C2 变化先评估 diff，由主线程确认后恢复。C3 或任何推翻目标、核心对象、状态机、文件所有权或验收方式的变化，应终止旧任务；旧线程只交接可复用结果，新线程不得继承旧聊天全文，只接收新权威、新任务契约和必要代码状态。

### 11.7 验收与恢复

主线程只有在以下条件满足后才能恢复受影响任务：

- 用户确认已完成（如果需要）；
- 活动权威已一次更新并通过文档检查；
- 旧内容已删除或进入隔离归档；
- 所有受影响线程完成 `REBASE_ACK`，或者旧线程已终止并建立替代任务；
- 文件所有权重新确认，没有两个线程同时修改同一文件；
- 验证计划按新风险重新选择，没有沿用已经失效的旧断言。

权威变化只触发受影响范围的重新评估，不自动要求所有线程重跑全量测试。主线程在波次合流后仍只执行一次必要的跨模块集成门禁。
