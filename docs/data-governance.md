# 数据治理与基础数据体系

本文件是曜核跨对象的数据治理总览，面向产品、设计、开发和后续维护人员。它负责说明数据分层、字段分类、证据、质量、索引、生命周期和过时规则的处理方式。

具体业务对象的关系和状态由[领域模型](domain-model.md)负责，用户结果和交互要求由[产品需求](product-requirements.md)负责，模块如何分析、索引和调用由[系统架构](system-architecture.md)负责。本文件不建立第二套 Knowledge、Media 或 CreationTask 事实源。

当前文档定义的是应达到的产品和数据契约，不代表源码已经全部实现。实现审计必须以代码、迁移、实际运行结果和真实客户端验收为准。

## 1. 先用一句话理解

曜核的数据链路是：

```text
原始资料/原始视频
→ 来源与工作区权限
→ 技术分析和可回查证据
→ 规范字段和业务语义
→ 带证据的知识断言/素材断言
→ 用户确认、纠正和使用限制
→ 结构化/全文/语义索引
→ Agent 候选包
→ CreationTask、时间线和成片
```

每一层解决的问题不同：

- **原始数据**回答“用户到底上传了什么”。
- **证据**回答“系统为什么这样理解”。
- **语义字段**回答“不同说法如何归为同一个概念”。
- **断言**回答“这份资料或这段画面具体说明了什么”。
- **权限与资格**回答“能不能被使用、自动选用或发布”。
- **索引**回答“数据量很大时如何快速找到它”。
- **使用反馈**回答“哪些候选被采用、替换或长期没有使用”。

来源、事实、权限、质量、热度和索引不能塞进同一个标签字段。

## 2. 数据分层总览

| 层 | 主要对象 | 解决的问题 | 是否事实源 | 主要产生者 |
| --- | --- | --- | --- | --- |
| 工作区与身份 | Workspace、成员、共享授权、任务范围授权 | 谁能看、改和使用数据 | 是 | 后端与授权用例 |
| 来源与出处 | SourceConnector、SourceItem、source_ref、origin_type | 数据从哪里来、属于哪一版 | 是 | 导入和连接器 |
| 原始内容 | KnowledgeItem、MediaAsset、原始视频/图片/音频/文档 | 用户实际保存的内容是什么 | 是 | 用户和接收流程 |
| 技术分析 | 元数据、镜头边界、ASR、OCR、关键帧、质量检测 | 文件和画面客观检测到了什么 | 分析事实 | Worker 和模型 |
| 证据 | EvidenceRef、AssetAnalysisRecord、原文定位、源时间范围 | 每个判断能否回查 | 是 | 分析流程 |
| 规范字段 | SemanticFieldDefinition、字段别名、值类型、单位规则 | 同义词和中英文表达如何统一 | 是 | 系统治理和用户维护 |
| 业务语义 | BusinessObject、KnowledgeClaim、AssetAssertion | 对象、动作、型号、参数、场景是什么 | 是，带状态 | 资料解析、模型、用户 |
| 上下文与修复 | AssetContextNote、CorrectionRecord、用户确认 | 用户补充了什么、修正了什么 | 是，带版本 | 用户和修复用例 |
| 使用资格 | ContentUseState、auto_selectable、发布资格 | 是否允许人工、自动或发布使用 | 是 | 用户和业务用例 |
| 检索索引 | 全文、结构化、向量、重排索引及版本 | 如何快速找到候选 | 否，可重建 | Indexer |
| 使用反馈 | UsageRecord、UsageHeat、接受/替换记录 | 候选实际是否有用 | 派生事实 | 任务和用户操作 |
| 创作引用 | CandidateBundle、Plan、CreationTask、TimelineVersion | 哪些资料实际被采用 | 是 | Agent 和创作流程 |
| 派生产物 | 代理文件、预览、配音、字幕、成片、平台版本 | 如何生成和回看结果 | 是，均需回溯来源 | Worker 和制作流程 |

## 3. 字段体系一览

所有主要对象都应优先具备 `id`、`workspace_id`、版本、状态、创建时间和更新时间。以下是需要建设的核心字段组；内部字段可以使用英文名，界面必须显示用户能理解的中文名称，并标出来源。

| 字段组 | 代表字段 | 用途 | 谁产生 | 是否可以直接修改 |
| --- | --- | --- | --- | --- |
| 身份与归属 | `id`、`workspace_id`、`asset_code`、`clip_code`、`parent_ref` | 区分对象、归属工作区和父子关系 | 系统 | 不直接改；通过新版本或迁移处理 |
| 版本与状态 | `version`、`analysis_version`、`status`、`supersedes_ref` | 区分当前版本、历史版本和替代关系 | 系统 | 通过状态转换修改 |
| 来源 | `source_ref`、`origin_type`、`canonical_url`、`external_id`、`captured_at`、`fetched_at` | 记录来源和采集时间 | 导入流程 | 用户可补充，不能覆盖原始出处 |
| 文件与完整性 | `original_ref`、`proxy_ref`、`media_type`、`duration`、`width`、`height`、`codec`、文件摘要、接收状态 | 证明文件是什么以及是否完整 | 接收流程 | 原始文件不可改；代理可重建 |
| 时间范围 | `start_ms`、`end_ms`、`source_time_range`、时间基准 | 定位片段、对白、OCR和动作 | 分析与用户修复 | 可通过新版本调整 |
| 分析来源 | `modality`、`model_or_rule`、模型版本、`sampling_coverage`、分析时间 | 说明由视觉、音频、OCR还是规则产生 | Worker | 不覆盖历史记录 |
| 观察内容 | `observation`、`transcript_ref`、OCR文本、镜头边界、关键帧引用 | 记录直接观察到的内容 | 模型与规则 | 用户不能直接改原始观察，可提交纠正 |
| 推断内容 | `inference`、候选对象、候选动作、候选型号 | 表达模型推测，不冒充事实 | 模型 | 用户可确认、拒绝或修正 |
| 字段定义 | `canonical_id`、显示名称、英文名称、别名、父字段、值类型、单位规则、适用对象、修订号 | 统一“包装机/封装设备”等表达 | 系统与管理员 | 通过字段定义修订，不改历史值 |
| 字段值 | `subject_ref`、`predicate` 或 `field_ref`、`value`、`unit`、`qualifiers` | 表达某个对象或片段的具体值 | 资料、模型、用户 | 追加新断言，不覆盖旧值 |
| 证据定位 | 原文件引用、源时间段、页码、段落、表格单元格、URL版本、关键帧引用 | 让每个事实可以回查 | 分析和资料解析 | 不应丢失；修复时追加 |
| 置信与状态 | `confidence`、`confidence_class`、`candidate/confirmed/rejected/unresolved` | 区分候选、确认、冲突和未知 | 系统与用户 | 用户通过确认/纠正改变状态 |
| 用户说明 | `note_text`、录音引用、来源类型、覆盖时间范围、语义完整度、未决问题 | 补充模型无法从画面得到的上下文 | 用户 | 可追加、暂停后继续 |
| 使用限制 | `use_state`、来源类型、是否自动选用、是否发布 | 表达可用范围 | 用户与授权用例 | 只能由有权操作修改 |
| 修复记录 | 原值、新值、作用范围、理由、证据、操作者、时间、撤销关系 | 保留数据修复历史 | 用户和修复用例 | 追加，不删除原分析 |
| 索引状态 | 索引类型、源版本、索引版本、模型版本、覆盖范围、构建时间、状态、失效原因 | 判断搜索结果是否新鲜 | Indexer | 可重建，不是事实源 |
| 使用反馈 | `task_id`、`timeline_version`、用途、采用/替换结果、替换原因、使用时间 | 让系统知道候选是否真正有用 | 创作流程 | 由真实使用行为产生 |

字段值必须有类型。数值字段不能只存一段文字；例如产能应拆成数值、单位、适用条件和来源。枚举字段用于稳定状态，关系字段用于对象之间的关联，自由文本用于原始说明和无法规范化的内容，向量只用于召回，不保存事实。

### 3.1 所有资产共用的字段与各自专用字段

素材库、视频库、声音库、人物库和知识库都要纳入治理，但不共用一套平面标签。所有资产先拥有一组通用字段：

| 通用字段组 | 典型字段 | 说明 |
| --- | --- | --- |
| 身份 | `id`、`workspace_id`、`asset_type`、显示编号 | 说明它是什么资产、属于哪个工作区 |
| 来源 | `source_ref`、`origin_type`、上传者、采集设备、采集时间 | 说明从哪里来，不能直接推导是否可发布 |
| 版本 | `version`、`supersedes_ref`、当前状态 | 说明哪一版有效、哪一版被替代 |
| 使用范围 | `use_state`、可见性、自动使用资格、发布资格 | 说明谁能用、能用于什么用途 |
| 证据 | 来源位置、分析记录、用户说明、确认记录 | 说明判断依据 |
| 质量/能力 | 质量观察、能力状态、不可用原因 | 说明是否清楚、是否适合某种生成或播放 |
| 使用反馈 | 使用任务、采用/替换结果、最后使用时间 | 说明实际是否被用户接受 |

通用字段只负责资产治理，不负责表达所有业务含义。各类资产还需要专用字段：

| 资产类型 | 专用语义字段 | Agent 使用时要回答的问题 |
| --- | --- | --- |
| 视频、图片、音频素材 | 时长、画面方向、镜头、Clip、主体、动作、场景、OCR、转写、画质、可裁切区域 | 这段内容展示了什么，能否作为某个镜头 |
| 声音档案 | 参考音频、参考文字、语言、发音、噪声、清晰度、模型能力、声音版本、使用范围 | 能否用这个声音生成哪种语言的配音 |
| 人物形象档案 | 参考图/视频、人物标识、可用景别、背景、动作、口型能力、形象版本、使用范围 | 这个人物能否出镜、口型同步或发布 |
| 企业知识 | 标题、正文、语言、产品对象、主题、段落/页码/表格定位、有效版本、冲突状态 | 哪些内容可以作为事实、文案或选题依据 |
| 产品/业务对象 | 对象类型、名称、别名、关系、属性和适用范围 | 这是什么产品、属于哪个系列、和哪些部件有关 |
| 视频模板 | 适用场景、画幅、输入要求、可修改参数、语言支持、版本 | 这个模板适合什么内容，缺什么输入 |
| 用户偏好 | 适用用户、语言、表达习惯、禁用词、版本 | 这个用户通常希望怎样表达 |

用户偏好不属于企业知识，人物形象不等于声音，声音参考不等于已完成的声音克隆，视频画面也不等于产品事实。它们可以在同一条任务中被关联，但不能互相替代。

声音和人物还需要单独保存授权范围。当前的 `use_state` 解决产品内“能否使用”，但还需要补充可理解的授权记录或授权字段，至少能表达声音/形象可以用于参考、生成、口型同步、内部预览和公开发布中的哪些范围，以及由谁确认、何时生效、何时撤销。这个授权不应变成所有用户上传时都必须填写的复杂法律表单；对用户自己的资产可以采用简单声明，对共享、克隆和公开发布等高影响用途再要求明确确认。

## 4. 核心对象和关系

```text
Workspace
├── SourceItem / KnowledgeItem
│   └── KnowledgeClaim
├── MediaAsset
│   ├── 技术镜头边界
│   ├── Clip（逻辑语义片段）
│   │   ├── AssetAnalysisRecord
│   │   ├── AssetContextNote
│   │   └── AssetAssertion
│   └── 代理、缩略图和其他可重建产物
├── BusinessObject
├── SemanticFieldDefinition
├── PersonProfile / VoiceProfile
└── ContentUseState / CorrectionRecord / UsageRecord

KnowledgeClaim、AssetAssertion 和用户纠正共同支持检索，但它们必须继续回指 KnowledgeItem、MediaAsset 或 Clip 的具体版本。索引不能反过来成为事实源。
```

### 4.1 五分钟视频的实际关系

用户上传一条五分钟视频后，系统先建立一个 `MediaAsset`，例如 `asset-A001`，保存原始文件、时长、尺寸、来源和接收状态。接着按技术镜头边界、连续动作、音频、OCR和用户说明生成分析记录。

随后生成的是逻辑 `Clip`，例如：

| Clip | 原始时间范围 | 语义 | 证据状态 |
| --- | --- | --- | --- |
| `clip-C001` | 00:12–00:38 | 设备正在进行进料操作 | 画面观察确认，型号待确认 |
| `clip-C002` | 00:40–01:05 | 操作员调整设备参数 | 画面观察和语音说明一致 |
| `clip-C003` | 02:10–02:42 | 展示封口后的产品效果 | 画面可见，效果能力需资料确认 |

这些 Clip 通过 `asset_id + start_ms + end_ms` 指向同一条原始视频。它们可以重叠，也可以由多个技术镜头组成。播放器代理、缩略图和下载片段都可以重新生成，不能取代原始视频。

Agent 收到“做一条 45 秒视频，展示进料过程并说明维护简单”的请求时，先召回 `clip-C001`，再从 KnowledgeClaim 中寻找“维护简单”的资料证据。如果资料中没有这个结论，Agent 必须提出缺口，不能因为画面相似就自行写出这个卖点。

## 5. 数据生命周期

一条素材或知识从进入系统到被使用，至少经历以下状态：

```text
发现候选
→ 接收中
→ 已接收
→ 技术分析中
→ 已有分析但待补充说明
→ 可检索
→ 可自动选用
→ 被任务采用
→ 被修复/被替代/被撤权
→ 归档或删除
```

状态之间必须区分：

- **可接收**不等于已经完整分析。
- **可检索**不等于可以自动选用。
- **可自动选用**不等于已经被用户确认所有事实。
- **被任务采用**不等于以后所有任务都必须继续使用。
- **被替代**不等于历史任务可以丢失来源。
- **归档**不等于立即删除原始数据。

原始内容、用户说明、分析记录、断言、纠正和任务采用都必须保留各自版本。索引、向量、缩略图和代理文件可以失效后重建；原始文件、知识版本和已采用任务输入不能用索引重建时被静默删除。

## 6. 当前已经建立的基础

当前文档已经明确了这些重要基础：

1. Workspace 是数据隔离边界，权限不由客户端自报；具体规则见[认证与工作区边界](auth-workspace-boundary.md)。
2. 原始视频和知识内容不可被生成流程覆盖，Clip 是原始 MediaAsset 上的逻辑时间片段。
3. 画面、音频、OCR、用户说明和企业资料分别作为不同来源处理。
4. KnowledgeClaim、AssetAssertion 和 SemanticFieldDefinition 已经定义了知识事实、素材断言和规范字段的方向。
5. 用户可以用任意合理时长的语音或文字补充说明，不按固定秒数通过。
6. 来源类型、使用权限、自动选用资格、质量和热度已经被要求分开。
7. 检索已经规划为硬过滤、精确召回、语义召回、证据重排和使用反馈排序。
8. Agent 应该获得包含片段、时间范围、证据、来源、限制、冲突和待确认项的 CandidateBundle。
9. 中文、英文及其他已声明语言的任务内容独立保存，不能用一个语言版本的状态代表另一个语言版本。
10. 素材质量档案现在按清晰度、曝光、稳定性、构图、安全裁切、音频、OCR 可读性和动作完整度分别保存状态；分析器没有真实测量时明确保存 `unavailable`，不写入伪造分数。
11. 索引重建任务保存排队、运行、成功、失败和取消状态；源文件变化后的索引必须先标记过期，再由新的源版本重建。
12. 逻辑 Clip 具有独立 `version`，重分析产生的拆分、合并和无法映射的旧引用会保存解释记录。

这些是设计层的当前基线，不等于每一项已经在源码和客户端中贯通。

## 7. 仍需完善的部分

### P0：没有这些内容，数据量大后很快会失控

| 缺口 | 当前问题 | 需要补齐 |
| --- | --- | --- |
| EvidenceRef | 旧路径很多地方只有 `evidence_refs` 抽象引用 | **已落地素材链路**：统一保存原文件、片段时间范围、来源修订、分析版本、模型和采样覆盖；知识资料使用 claim 的定位引用 |
| 字段值类型与单位 | 旧 `value` 可以是任意内容，容易把“10吨/小时”和“很快”混在一起 | **已落地**：支持字段类型、单位族、允许单位、别名、适用对象和受限单位换算；不兼容单位会显式失败 |
| AnalysisRun | 分析版本存在，但一次分析运行的输入、参数、失败和资源信息还不完整 | **已落地素材分析运行**：记录输入修订/digest、参数、阶段、模型、状态和失败原因；真实长任务资源统计仍需接入 |
| IndexRecord | 当前说索引可重建，但没有正式记录索引是否新鲜 | **已落地素材索引记录**：记录索引类型、源修订/digest、模型/规则、覆盖范围、构建时间、状态和失效原因；知识索引仍需接入 |
| QualityProfile | 单个 `quality_score` 不足以解释画面是否可用 | **已落地素材质量档案**：八项指标分别记录 observed/unavailable/unknown 状态和原因；真实质量测量仍需接入 |
| 稳定的片段身份 | 自动重新切片可能让同一段画面获得新编号 | **已落地**：独立 Clip 版本号、时间重叠 lineage、旧引用迁移/无法映射解释均持久化；时间线实际自动替换仍需客户端接入 |
| 去重关系 | 同一视频反复上传或导入不同代理可能重复入库 | 使用文件摘要、来源标识、时长/尺寸和人工确认建立重复候选，不能静默合并不同来源 |

### P1：影响长期维护和用户修复成本

- **字段字典生命周期：**需要定义新增、别名、合并、拆分、停用和跨语言修改怎样影响旧断言与索引。
- **冲突处理：**需要明确“企业资料互相冲突”“用户说明与画面冲突”“两个用户确认冲突”时的状态和界面动作。
- **纠正传播：**需要把当前片段、整条素材、批次和多个选中片段的修复范围落成真实用例，并计算哪些任务需要提示或重算。
- **新鲜度：**资料、素材和索引需要显示最后分析时间、最后确认时间、最后使用时间以及是否因来源版本变化而过期。
- **多语言语义：**字段定义需要保存中文、英文和别名之间的规范关联；翻译值不能改变型号、数值、单位和适用条件。
- **使用反馈：**UsageRecord 需要记录用户保留、替换、跳过和替换原因，否则 UsageHeat 没有可靠输入。
- **归档与删除：**需要定义原始文件、派生产物、索引、历史任务和纠正记录分别如何归档、恢复和删除。
- **界面映射：**需要把内部字段转成“拍摄对象、正在发生的动作、来源、依据、是否可自动使用、待确认问题”等用户语言，不能把 JSON 或模型标签直接展示给用户。

### P2：数据规模和模型质量上来以后再完善

- 为不同产品和场景建立真实、独立、不过度重复的评估样本，分别测镜头切分、动作识别、型号归属、资料召回、候选接受率和纠正负担。
- 为结构化过滤、全文索引、向量索引和重排分别量测延迟、内存、磁盘和增量更新成本，不一开始引入无法证明必要性的远程向量数据库。
- 建立数据保留、备份、恢复、跨设备迁移和外接盘断开后的状态核对策略。
- 对第三方素材、客户素材、人物声音和公开发布分别建立可理解的来源和使用提示，不把来源类型直接当成法律结论。

## 8. 需要清理或禁止继续使用的旧理解

以下内容已经不属于当前数据模型：

- **项目空间不是当前版本的数据组织对象。**当前仍以 Workspace、Knowledge/Media 资产和 CreationTask 为主；项目留到后续版本重新定义。
- **固定时长说明不是规则。**用户可以说 1 分钟、5 分钟、暂停后继续或分多次补充，系统按语义覆盖和关键问题判断是否完成。
- **物理切碎原视频不是数据模型。**当前采用原始 MediaAsset 加逻辑 Clip；代理文件和导出片段不能成为新的原始事实。
- **平面标签不是事实库。**标签是断言和用户组织偏好的展示/检索投影。
- **向量相似度不是事实正确率。**型号、参数、权限和发布资格必须通过字段、证据和使用状态核对。
- **Episode、Batch、repo.today、聊天记录、localStorage 和内存对象不能重新成为生产事实源。**现有文档中提到它们，是为了说明旧路径不得进入新的写链路。
- **单一总质量分数不能代替质量解释。**后续实现应逐步拆分质量维度，在迁移完成前保留旧字段的来源和含义，不能直接删除历史数据。

## 9. 推荐建设顺序

1. 先冻结字段字典、证据引用、值类型/单位、状态和版本规则。
2. 再让素材接收、分析、用户说明和纠正全部写入同一套对象与版本。
3. 然后建设可重建的结构化、全文和语义索引，并记录索引新鲜度。
4. 再接入 CandidateBundle，让 Agent 只消费带证据和限制的候选。
5. 最后根据真实用户采用和替换记录调整排序、热度和模型分析策略。

每一步都必须保留原始数据、可回查证据和历史版本。只有这样，素材库变大以后，系统才有机会知道“这是什么”“为什么这么认为”“能不能用”和“用了以后效果如何”。

审计得到的第一批实施顺序如下：

1. **P0：把字段/断言状态接入所有用户确认和纠正入口。** 当前素材候选、知识候选、确认状态和证据已经分别持久化，但素材断言的确认 UI 和跨对象冲突处理仍需贯通。
2. **P0：建立稳定的逻辑 Clip 版本号和旧任务引用迁移。** 当前已有时间重叠 lineage，下一步要让时间线引用明确指向版本并在拆分/合并后可解释恢复。
3. **P1：把 IndexRecord 接入增量重建、Knowledge 检索和 UsageRecord 回执。** 让索引新鲜度、修复传播和排序反馈真正闭环。
4. **P1：QualityProfile、来源/授权和多语言语义映射。** 让 Agent 在选择素材、声音和人物时能说明质量、用途和语言限制。
5. **P2：规模化性能、评估样本、备份恢复和归档删除。** 等 P0/P1 的事实模型稳定后再量测和扩展基础设施。

目前不能把以下静态存在当成已完成：素材 payload 中出现 `facts` 不等于已经存在统一断言；返回 `visual_similarity` 不等于型号或动作被确认；有 `updated_at` 不等于存在版本 lineage；有知识全文搜索不等于存在可重建的语义索引。后续每个实现批次都按“代码入口、持久化行、真实消费者、用户可见结果”四层验收。

## 11. 素材证据到输出观察闭环（2026-11-13）

本轮完成了素材视频生产链路的四段闭环：候选搜索从治理库回带片段级或素材级 `EvidenceRef` ID；Agent/用户采用时保存候选快照、采用身份和时间，并在采用事务内重新校验工作区权限、素材资格和证据有效性；真实渲染完成后，`material_segment_usage` 记录任务和实际时间线版本；输出观察结果按当前绑定的时间线片段回带素材来源、源时间范围、时间线范围、匹配理由和 `evidence_ref_ids`。

定向证据为：数据治理与知识专项 `517 passed`；候选→schema 接缝、精确任务/时间线使用记录和真实输出观察回带专项 `12 passed`。旧使用记录没有时间线版本时继续返回当前任务版本并标记为 `current`，不能把历史行猜成某个版本。

参考视频阶段已完成第一步：复用受治理的 `MaterialAsset`、逻辑片段和 `EvidenceRef`，持久化 `study/shot list`，并提供绑定当前任务与时间线版本的结构 `compare`。study 创建前必须有当前源修订的素材分析；源文件修订变化会把 study 标记为 `stale`。当前 compare 只输出可验证的时长、镜头数和节奏结构指标，视觉与音频观察明确为 `unavailable`，仍需实际输出的有界帧/音频检查，不能把结构指标或单一相似度分数当成逐镜头复刻验收。

## 12. 参考视频 study 与结构 compare（2026-11-13）

已落地的接口为：

- `POST /api/production/materials/{asset_id}/reference-study`：基于当前源修订的治理素材分析生成 study；每个 shot 绑定素材片段和证据 ID。
- `GET /api/production/reference-studies/{study_id}`：回读 study，并在源文件修订变化后持久化 `stale`。
- `POST /api/production/reference-studies/{study_id}/compare`：重新核验参考素材的 `ContentUseState` 和有效证据，只接受当前任务的当前 `timeline_version_id`，保存结构 compare 报告和参考证据 ID。
